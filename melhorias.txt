# 1. OBJETIVO FINAL

A arquitetura correta deve ser:

```text
segments
    ↓
service_templates
    ↓
business_segments
    ↓
services
    ↓
professional_services
```

Onde:

### `segments`

É o catálogo GLOBAL dos segmentos comerciais disponíveis no Agendou.

### `service_templates`

É o catálogo GLOBAL de serviços sugeridos pertencentes a cada segmento.

### `business_segments`

Representa quais segmentos um determinado estabelecimento escolheu.

### `services`

Continua sendo o catálogo REAL e independente de cada estabelecimento.

Quando o estabelecimento seleciona um serviço sugerido:

```text
service_template global
        ↓
COPIAR
        ↓
service do estabelecimento
```

Depois da cópia, o serviço pertence exclusivamente ao estabelecimento.

Alterações futuras no catálogo global NÃO podem alterar automaticamente o serviço existente do estabelecimento.

# 13. DOWNGRADE

A auditoria encontrou uma lacuna no downgrade.

Implemente uma política segura e consistente.

Preferência:

Quando um estabelecimento possui mais segmentos ativos do que o novo plano permite, NÃO exclua dados silenciosamente.

O sistema deve:

* impedir novas ativações que ultrapassem o limite;
* preservar os segmentos existentes;
* identificar o excesso;
* impedir novas ativações incompatíveis;
* informar claramente o estabelecimento de que precisa adequar os segmentos antes de utilizar o novo limite.

Se a arquitetura atual exigir uma solução diferente, escolha a alternativa mais segura que preserve dados e seja consistente com o billing existente.

NUNCA apagar segmentos ou serviços silenciosamente por downgrade.

* pode permanecer associado a serviços legados que realmente não possuem segmento;
* serviços existentes devem ser preservados.

Se necessário, use um identificador técnico claro para diferenciá-lo dos segmentos comerciais.

Não edite migrations históricas já aplicadas de maneira destrutiva.

Como a migration anterior:

```text
20260907000000_segments_service_catalog.sql
```

já existe no histórico local, prefira criar uma migration corretiva posterior.

A migration corretiva deve:

* criar `segments`;
* popular os 20 segmentos;
* corrigir `service_templates`;
* migrar a estrutura antiga com segurança;
* preservar serviços;
* remover dependências incorretas;
* remover triggers de sincronização incorretos;
* corrigir `business_segments`;
* preservar dados;
* ajustar RLS;
* corrigir catálogo público.

Não execute migrations em produção nesta tarefa.

Apenas crie o SQL e valide localmente.

---

# 23. IDEMPOTÊNCIA

As novas migrations devem ser seguras e consistentes com o padrão do projeto.

Evite:

```text
CREATE POLICY
```

sem verificar se já existe quando houver possibilidade de reexecução no contexto de desenvolvimento.

Evite constraints duplicadas.

Use mecanismos apropriados como:

```text
IF NOT EXISTS
```

quando suportado.

Quando `IF NOT EXISTS` não existir para determinada operação, utilize abordagem segura.

# 24. TESTES OBRIGATÓRIOS

Amplie os testes.

Além dos testes existentes, crie testes para:

### Segmentos

* os 20 segmentos existem;
* códigos são únicos;
* `Sobrancelhas & Cílios` é um único segmento.

### Templates

* catálogo global existe;
* templates pertencem a segmentos globais;
* quantidade correta de serviços por segmento;
* durações corretas;
* não possuem `business_id`;
* não são serviços vivos.

### Cópia

* template pode ser copiado;
* cópia gera novo `service_id`;
* preço pode ser definido independentemente;
* duração pode ser alterada;
* alteração do template não altera o serviço;
* exclusão do serviço não exclui template.

### Planos

* Basic = 1 segmento;
* Medium = 2;
* Unlimited = ilimitado;
* Trial = ilimitado;
* serviços ilimitados em todos.

### Downgrade

Testar cenário:

```text
Medium
2 segmentos
↓
Basic
```

Não deve apagar dados.

### Geral

* `Geral` não aparece no catálogo público;
* `Geral` não conta como segmento comercial;
* serviços legados continuam preservados.

### Isolamento

Testar que negócio A não consegue acessar/modificar dados de negócio B.

### Catálogo público

Testar:

* somente serviços do estabelecimento;
* somente serviços ativos;
* agrupamento por segmento;
* ausência de `Geral`.
